# Native window sizing: research and adaptation limits

Research verified 2026-10-26 against the installed Apple SDK and the current Shoji sources. This section describes facts and an independently proposed adaptation policy; it is not a claim that generic native size negotiation has been implemented or live-validated. No engine code, live windows or system settings were changed by this investigation.

## Public accessibility exposes size, not a universal constraint contract

The installed `AXAttributeConstants.h` defines `AXPosition` as a top-left screen position and `AXSize` as element dimensions, both in **points**. Resizable windows should offer writable size, and movable windows should offer writable position. `AXUIElementIsAttributeSettable` can establish whether a particular attribute is writable; that is a capability observation, not minimum/maximum geometry. [SDK position and size definitions](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXAttributeConstants.h:610), [settable query](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXUIElement.h:184).

The inspected generic AX attribute catalog has no `AXMinSize` or `AXMaxSize` declaration. `AXMinValue` and `AXMaxValue` describe the range of an element's `AXValue`, such as a slider or scrollbar; they are not a documented window-size constraint pair. An application may expose custom attributes, and `AXUIElementCopyAttributeNames` can enumerate supported names, but custom behavior must be probed and documented per application rather than treated as a universal contract. [SDK scalar range definitions](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXAttributeConstants.h:367), [attribute enumeration](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXUIElement.h:116).

AppKit does provide `NSWindow.minSize`, `maxSize`, `contentMinSize` and `contentMaxSize`, but these are properties of an application's own NSWindow object, not a documented remote AX query. The SDK explicitly notes that these min/max properties are ignored when using Auto Layout. Even an in-process property read is therefore not a universal description of effective application resizing. [Apple minSize](https://developer.apple.com/documentation/appkit/nswindow/minsize), [contentMinSize](https://developer.apple.com/documentation/appkit/nswindow/contentminsize), [SDK declarations and Auto Layout note](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/AppKit.framework/Headers/NSWindow.h:560).

## Request success is not an exact-frame presentation acknowledgment

`AXUIElementSetAttributeValue` sends a value to an accessible element and returns an `AXError`. Its documentation lists unsupported attributes, invalid elements/values, messaging failure and incomplete application support. It does **not** promise that a successful size setter is a WindowServer presentation barrier or that the exact requested dimensions are displayed when it returns. The API exposes no configure/ack serial linking an individual size request to later native frame observations. [SDK setter contract](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXUIElement.h:207).

The AX interface is request/reply messaging with configurable timeouts. A call returning success is stronger than merely queueing a local command, but its documented success condition must not be expanded into compositor synchronization. Timeout handling is also not resize rejection: keep messaging errors separate from a valid observed size that differs from a request. `AXUIElementSetMessagingTimeout` set on one element affects that exact object; setting it on the system-wide element sets the process's global timeout. [SDK timeout contract](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXUIElement.h:387).

`AXWindowResized` is documented as being sent at the **end** of a window resize. The generic `AXResized` notification only says that an element resized. Neither includes a size-request serial. Notification support must be checked: registration may return `kAXErrorNotificationUnsupported`. A notification is a prompt to sample geometry, not proof that a specific pending request was accepted exactly. [SDK window notification](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXNotificationConstants.h:126), [generic notification](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXNotificationConstants.h:280), [registration errors](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks/HIServices.framework/Headers/AXUIElement.h:609).

It remains possible for application processing, internal resize animation, compositor publication or observation to lag. The SDK does not specify a delay after which a nonmatching frame proves a minimum. Shoji's earlier owned AppKit fixture itself needed a settling loop before WindowServer readback matched requested geometry; that is local evidence for deferred presentation, not proof of every application's AX timing. [Prior owned validation](SCROLL_FEATURES_VALIDATION.md).

## Native window frame versus client content

AX geometry belongs to the accessible element. Applied to the top-level native window, it is a whole-window frame policy; it must not be silently treated as the content size used by a Wayland client. AppKit has distinct `setFrame:display:`, `setContentSize:`, `frameRectForContentRect:` and `contentRectForFrameRect:` APIs precisely because those geometries differ. Conversion depends on the native window's style/decorations. [SDK geometry conversions](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/AppKit.framework/Headers/NSWindow.h:285), [frame and content setters](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/AppKit.framework/Headers/NSWindow.h:348).

## Current Shoji seams

The inspected implementation has these useful boundaries:

- `src/macos/frame_darwin.odin`: `apply_frame_now` samples previous WindowServer bounds, performs AX writes and marks the desktop dirty. `write_accessibility_frame` avoids redundant size writes for pure moves/resizes; combined changes use size → position → size because some apps clamp at their old location. It reports AX errors, not accepted geometry.
- `src/macos/backend_darwin.odin`: `window_frame` currently reads AXPosition and AXSize independently into a zero-initialized Rect. A failed attribute read can therefore look like zero geometry. New observation code must retain validity explicitly rather than interpreting default zeros as native size constraints.
- `src/macos/window_observation_darwin.odin`: collection reads native geometry; reconciliation currently updates the model frame from the observation. Requested logical sizing, pending native requests and observed actual geometry need distinct roles if asynchronous acceptance is added.
- `src/macos/window_visibility_darwin.odin`: the current per-window notification list includes generic `AXResized` and `AXMoved`; window-specific end notifications may be added when supported, with polling fallback.
- `src/macos/frame_updates_darwin.odin`: nested `SLSDisableUpdate`/`SLSReenableUpdate` bookkeeping is a presentation mechanism, not a documented cross-application resize transaction or a client acknowledgment protocol.

These are source observations, not instructions to change unrelated policies or infer constraints from the first readback.

## Recommended accepted-size adaptation

The following is an engineering proposal, not an Apple guarantee:

1. **Retain intent.** Keep the user's fixed/proportional request and explicit min/max settings. Keep a separate observed whole-window frame and its validity. A mismatched observation must not overwrite the user's sizing request.
2. **Version requests.** Track the window's owner identity, lifetime/generation, newest desired frame, write result, pre-write observed frame and timestamps. Replace superseded requests instead of accumulating stale animation or AX writes. Discard results for older generations, reused IDs and changed owners.
3. **Observe without forcing.** After a successful write, sample on supported resize notifications and a bounded timer. Accept only valid finite positive bounds for the same window identity. If AX and WindowServer disagree, treat that as unresolved observation rather than a capability limit.
4. **Require evidence of settling.** A sequence of unchanged pre-write frames immediately after the setter is not sufficient. Prefer a valid post-request change or end-of-resize signal followed by a quiet, converged frame. Notifications have no serial, so attribution is still heuristic. Defer adaptation during user drags, column gestures, running resize animation, Space transition, fullscreen/minimize/restore, or newer pending intent.
5. **Adapt to accepted geometry provisionally.** If the latest request has a credible stable native result different from the requested frame, lay out its neighbors around that actual result and expose the discrepancy. Treat it as this window's current accepted size, not a permanently learned `min_width`/`max_width`. Aspect ratio, increments, decorations, position, state or dynamic content can explain the same mismatch.
6. **Expire assumptions.** Clear/retry provisional acceptance after new explicit sizing intent, app/window state changes, display changes or a later native resize. Preserve manual bounds separately. A timeout is unresolved/unresponsive, not evidence that the previous size is the application's minimum.

For example, request width 600 from an 1100-wide window. Three rapid 1100-wide reads before AppKit commits are stale evidence; they must not teach a minimum of 1100. If a later settled native result is 720, the layout may provisionally use 720 to avoid overlap, while retaining the 600 request. A subsequent successful 650-wide native resize invalidates the earlier provisional assumption. This example is a proposed acceptance fixture, not a measured application trace.

## Coordinated resizing

A useful first target is **one layout generation and one presentation timeline**, not a fictitious atomic resize across arbitrary apps. Plan all target frames from one model snapshot, issue only the newest requests, track each member's observed readiness independently, and retarget the common presentation when an application accepts a different size. Keep a bounded fallback for an app that never settles so it cannot stall every other window indefinitely.

Any presentation-suppression scope must be balanced on success and failure. Existing private update calls have no public cross-client atomicity contract; their existence does not justify reporting fully synchronized native client rendering. Owned-window tests can validate coordinator scheduling and cleanup, while foreign-AX acceptance and rendering still need separate live evidence.

Required test traces include delayed success, valid clamping, partial AX read failure, no notification support, request supersession, interactive resize, owner/ID reuse, timeout then recovery, accepted-size changes after content/layout changes, and a nonresponding member of a multi-window resize. Record requested and observed frames plus generation/status, not an invented permanent constraint.

## Implementation evidence — 2026-10-26

The research above records the starting point. Shoji now implements per-request, generation-checked accepted-size observations in `src/engine/size_feedback.odin` and `src/macos/size_feedback_darwin.odin`. Two stable native observations, at least 60ms apart and after a 150ms quiet interval, allow provisional adaptation. Observation waits during gestures and coordinated resizing. It verifies native window ownership and ignores failed or invalid geometry. It does not claim universal constraint discovery or an AX presentation barrier.

Column/row requests survive adaptation, and explicit retries or changed sizing context invalidate both axis adjustments. The resize coordinator shares one timeline with camera and neighbor motion. See [native sizing validation](SCROLL_SIZING_VALIDATION.md) for measured evidence and remaining gaps.
