# Niri behavior relevant to Shoji

Investigated 2026-10-25 against Niri's official documentation and source. These are behavior targets, not a claim that Shoji already implements them. The upstream `main` documentation also contains unreleased features; this note avoids relying on items marked “next release.”

## The distinction that matters

Niri's source explicitly separates scrollable tiling from the choice of workspace system. Its layout model manages monitors, workspaces, columns and a viewport offset; its rendering code handles Wayland surfaces, textures and transformed render elements. **Engineering inference:** Shoji can adopt the layout semantics without replacing WindowServer, while exact rendering and input parity require capabilities beyond merely computing window frames. This research does not establish which of those capabilities macOS exposes. [Layout source](https://raw.githubusercontent.com/niri-wm/niri/main/src/layout/mod.rs), [scrolling source](https://raw.githubusercontent.com/niri-wm/niri/main/src/layout/scrolling.rs).

## Behavior inventory

| Behavior | What Niri does | Implication for a Shoji design (inference) |
| --- | --- | --- |
| Horizontal strip | Columns extend beyond the visible viewport. Each monitor owns its strip; overflow never appears on its neighboring monitor. Opening a window preserves existing window sizes. | Store logical column positions separately from physical window frames. Per-monitor clipping and keeping invisible windows unreachable are independent backend requirements. [README](https://github.com/niri-wm/niri) |
| Viewport focus | Focus can reveal an off-screen column at an edge, always center it, or center only when the previous and new columns cannot fit together. Widths can be fixed or proportional; width and height presets are configurable. | Implement focus-to-viewport policy as layout math, preserving the user's column widths. [Layout configuration](https://niri-wm.github.io/niri/Configuration%3A-Layout.html) |
| Vertical tiles and tabs | A column can show windows as vertical tiles or as equally sized tabs. Windows can be consumed into or expelled from a column. A clickable indicator selects tabs; tabbed columns support fullscreen with multiple members. | Column membership, row weights and active tab belong in the model. Hiding inactive members reliably and drawing an indicator are separate platform work. [Tabs](https://niri-wm.github.io/niri/Tabs.html) |
| Dynamic workspaces | Every monitor has its own ordered workspace list and trailing empty workspace. Opening there appends another empty workspace; unused interior workspaces disappear after leaving them. Named workspaces persist while empty. Workspace numbers mean positions on the focused monitor. | Use stable internal workspace IDs plus per-monitor ordering; do not use display indices as identity. Native macOS Spaces are a separate possible backend, not inherent to these semantics. [Workspaces](https://niri-wm.github.io/niri/Workspaces.html) |
| Monitor hotplug | Workspaces migrate when an output disappears and can return when it reconnects. Upstream tracks original-output preferences; actively adding windows resets that association to reduce surprise. | Record ownership and recovery policy, and validate reconnect behavior independently of basic single-monitor tiling. [Layout source](https://raw.githubusercontent.com/niri-wm/niri/main/src/layout/mod.rs) |
| Floating dialogs | Floating windows stay above tiled windows and do not scroll. Each workspace has its own floating arrangement. Parent-associated and fixed-size windows float automatically unless rules override it. | Give dialogs an explicit owner and layer rather than treating all windows as members of the scrolling strip. [Floating windows](https://niri-wm.github.io/niri/Floating-Windows.html) |
| Three sizing modes | Full-width columns retain gaps and reserved space. Maximizing a window to edges retains the bar but removes gaps/borders. True fullscreen covers the whole screen; a settled focused fullscreen covers ordinary floating windows and the shell's top layer. | Keep tiling width, maximize and native/application fullscreen distinct. Niri does not promise every floating dialog is above true fullscreen; Shoji needs an explicit policy for system utility windows. [Fullscreen and maximize](https://niri-wm.github.io/niri/Fullscreen-and-Maximize.html) |
| Overview | Zoomed-out workspaces remain navigable with keyboard, scrolling and drag-and-drop; windows can be moved into existing or newly inserted workspaces. Different shell layers participate differently in the zoom. | A thumbnail navigator can reproduce navigation semantics. A live, spatially exact overview also needs window imagery, transforms, layering, clipping and hit testing. [Overview](https://niri-wm.github.io/niri/Overview.html) |
| Gestures | Three-finger horizontal swipes pan; vertical swipes switch workspaces. Four fingers open/close overview. Modifier-and-mouse gestures move/resize windows and pan/switch; dragging against edges scrolls the view. | Begin with keyboard actions and modifier-plus-scroll, then assess continuous gesture capture, cancellation, momentum and conflicts with macOS gestures. [Gestures](https://niri-wm.github.io/niri/Gestures.html) |

## Responsiveness is part of the behavior

Niri deliberately applies focus and layout actions immediately, independently of their visual animation. Input switches to the destination workspace at the start of a transition; overview interactions also become available immediately. Changes to windows left of the focused one should not make that focused window jump. These are useful acceptance criteria even for a non-compositor implementation. [Design principles](https://niri-wm.github.io/niri/Development%3A-Design-Principles.html).

Animations support easing or springs, including finger-release velocity. Related resize and viewport animations share timing where implemented. The clock supports deterministic testing and rendering for a predicted presentation time. Its redraw loop tracks each output's refresh cycle and throttles client callbacks even when only invisible content changes. **Inference:** animating asynchronous Accessibility frame requests alone cannot establish equivalent presentation guarantees; measure actual latency and frame pacing before claiming parity. [Animation configuration](https://niri-wm.github.io/niri/Configuration%3A-Animations.html), [animation timing](https://niri-wm.github.io/niri/Development%3A-Animation-Timing.html), [redraw loop](https://niri-wm.github.io/niri/Development%3A-Redraw-Loop.html).

## Suggested order of investigation

This is an engineering recommendation, not an upstream requirement:

1. Model and test columns, vertical tiles, viewport focus, persistent widths and immediate focus without touching the compositor.
2. Prove physical presentation: one monitor's overflow must never leak onto a neighbor; off-screen windows must remain recoverable and must not steal focus.
3. Add logical per-monitor workspaces, dialog ownership, tab visibility and monitor disconnect recovery, with a recovery path if Shoji exits.
4. Evaluate overview imagery and continuous gestures only after those correctness constraints hold. Describe thumbnail navigation honestly if live transformed windows cannot be supported.

The decisive first backend experiment is therefore **clipped horizontal scrolling across two displays with normal, floating and child windows**, not a fullscreen animation demo. A successful layout calculation alone does not prove this presentation behavior.
