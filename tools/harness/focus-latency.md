# System Settings focus-ring timing

On macOS 15.6 (24G84), two fresh System Settings launches were observed with a separate process polling on-screen WindowServer metadata at approximately 100 ms intervals. System Settings' main window appeared at x=832 while Shoji's ring was still at x=14 around the previous window. The ring's top surface later appeared at x=842, consistent with the Settings window's rounded inset. The measured delays between first observed window and first matching ring were approximately 532 ms and 210 ms, with sampling uncertainty of at least one poll interval. These tests observe visible window and surface geometry, not application focus eligibility, color, sublevel occlusion or every displayed frame; they do not establish the longer delays reported by the user.

During one activation, a separate five-second process sample showed Shoji's main thread in `refresh`, including synchronous AX attribute reads and `NSRunningApplication`/LaunchServices calls. Sampling is aggregated over the full period and does not establish the precise cause or duration of the cold-launch delay.

The source now calls `refresh_set_focus` after identifying the focused window. This immediately updates focus-ring surfaces before later refresh effects, observation and layout work, rather than waiting until the ordinary motion tick. It does not make application discovery asynchronous or prove that focus will be detected immediately. `tests.refreshed_focus_updates_the_ring_before_later_refresh_work` checks the ordering through the real ring planner with a mock drawing backend; the full deterministic suite passed 325 tests. A separate signed candidate built and reported its version; it has not been installed or used for a live before/after test. User testing and further investigation remain necessary before claiming that the observed cold-launch delay or intermittent multi-second cases are resolved.

Raw local metadata and a process sample are temporarily at `/tmp/shoji-focus-cold.kmomPJBr/` and `/tmp/shoji-focus-cold-stack.CDTSDQHL/`. They contain window geometry and process stacks; avoid committing broader system process data. The experiment left System Settings open and did not restart Shoji or Dock.

## VirtualBuddy keyboard focus

On the same macOS installation, repeatedly switching between the VirtualBuddy library and a saved VM exposed a separate focus mismatch. Raising the library returned AX error -25205 even though an independent query showed that macOS had focused the requested window. Shoji returned an error and retained the previous focus in its model. The source now accepts a failed raise only when the target application is frontmost and its independently queried focused window has the requested ID. A separate signed process using the corrected backend successfully focused the library in three alternating cycles. A regression test exercises both verified and unverified errors through the scroll-layout focus command. This does not prove that the user's reported freeze is resolved: a trace also recorded a synchronous window-frame call taking approximately 82 ms.

An exploratory call to the existing Dock focus-without-raise operation crashed Dock on this host. Dock restarted and the user confirmed that it and Space switching worked again. The source now disables that operation on arm64 macOS 15.6.0, but the guard is not installed in the running Dock payload. The crash mechanism and safety on other OS versions are unverified; do not repeat the private focus probe on the host. The corrected daemon and guarded payload were built separately and have not been installed. Live keyboard switching with the corrected daemon remains to be validated.

The corrected daemon was subsequently installed and its signature verified with access to the user keychain. The existing Dock payload was not replaced or reloaded; its focus guard is still not active. The user recorded a similar stall switching between Mail and Activity Monitor, so the VirtualBuddy raise error does not account for the general problem. A subsequent separate production-daemon capture alternated focus between those applications using commands and restored the original focus. It recorded 218 native frame calls, the longest 18.84 ms, and a maximum 84.84 ms between main-loop events. These timings show missed motion deadlines but do not establish the cause or reproduce the full duration of the recorded stall. Raw trace: `/tmp/shoji-mail-motion.json`.
