# Compositor coverage map (26A434 SkyLight)

Static reachability study over `artifacts/windowserver-26A434/ghidra/coverage-map.txt`
(2,569 visibility-relevant functions, generated by `MapCoverage.java` from the
exact-build mapped project). Scope: named direct calls only; indirect dispatch
flows are unknown, as the export header declares.

## Question

How much of "a window becomes visible / changes on screen" flows through the
hooked ordering choke point `CGXOrderWindowListSpaceSwitchOptions`, and what
bypasses it?

## Findings

### 1. The ordering family converges (123 functions reach the hook)

Every externally reachable ordering entry point funnels into the hooked
function: `__XOrderWindow(List…)`, `CGXOrderWindowListWithGroups`,
`start_order_window`/`finish_order_windows`, and the whole transaction
ordering set (`PKGTransactionOrderWindow`, `…OrderWindowGroup`,
`…OrderWindowGroupFrontConditionally`, `…SafeOrderWindowGroup`, ordering-group
add/remove/clear, system-level set/reset). Surface flush
(`__CGXFlushSurfaceInline`) also calls it. For **z-order-driven visibility
within a space**, the hook's coverage is complete as far as static evidence
shows.

### 2. Three visibility/geometry channels bypass the hook entirely

390 entry-like functions never reach the hook. The relevant families:

- **Space membership and switching** — `PKGTransactionAddWindowToSpace*`,
  `RemoveWindowFromSpace*`, `HideSpace`/`ShowSpace`,
  `SetManagedDisplayCurrentSpace`, `WillSwitchSpaces`,
  `RequestSwitchToSpaceForWindow`, `SetSpaceAlpha/Level/Shape/Transform`.
  A window becomes visible when its *space* becomes current: zero window
  ordering calls involved.
- **Surfaces** — `PKGTransactionBindSurface`, `SetSurfaceBounds/Opacity/
  ColorSpace/Resolution/LayerBackingOptions`, `PKGTransactionOrderSurface`,
  `_CGXActivateSurfaces`, `_CGXCompleteSurfaces`. Content presentation lives
  here; opacity and surface bounds change with no ordering call.
- **Window geometry** — `PKGTransactionSetWindowBounds`, `…LockedBounds`,
  `SetWindowTransform`, `SetWindowTransform3D`, `SetWindowBoundsPath`.
  Moving/resizing never reorders.

Plus direct visibility bookkeeping: `PKGTransactionSetGlobalVisibleWindowList`,
`CGXPackagesNoteWindowIsVisible`, `…AddVisibleWindowCount`.

### 3. All three channels are transaction-mediated

`PKGTransactionCommit` / `SLSTransactionPostCommit` have exactly four direct
callers: `_SLSTransactionCommit`, `__XTransactionCommitAsync`,
`__XTransactionCommitSync`, `sls_transaction_commit_ca`. None of the 59
`PKGTransaction*` mutators *calls* Commit — they are operations invoked *by*
the commit machinery (indirect dispatch; static analysis cannot follow it).
The model is: clients build transactions, commit through one of four
endpoints, and the commit machinery dispatches to mutators — some of which
(ordering) reach our hook, most of which (bounds/surface/space) mutate state
directly.

## Consequences for the gate architecture

- The current hook gates exactly one of four visibility channels
  (intra-space z-order). This matches the live evidence: our held window
  stayed invisible because its ordering call was held.
- A presentation gate with broad coverage must also cover **space switches**,
  **surface bind/opacity/bounds**, and **window bounds/transform**.
- Resolved (see `DISPATCH.md`): dispatch is a static global table at
  0x1e873d430, 140 × 16-byte entries indexed by op type, handlers called
  via `blraaz`. All handlers share the `(PKGTransactionContext*)`
  signature, so a generic per-op gate shim can wrap any subset — a pointer
  swap per op instead of inline patching. Ordering outside transactions
  (`__XOrderWindow`) still needs the existing inline hook.
- The pixel-level question (does the compositor present frames around the
  ordering hold?) is being answered separately with ScreenCaptureKit
  (`tools/harness/capture-probe`), pending guest Screen Recording consent.
