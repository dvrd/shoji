# Swipe presentation: existing evidence and gaps

Inventory date: 2026-10-28. This is a source and existing-evidence review, not a new live test. The working tree contains ongoing changes; the code descriptions below refer to the files inspected on this date. Unless otherwise stated, behavioral evidence is from macOS 15.6 (24G84), not a guarantee on other builds.

## Relevant external work

[Historical WindowServer research](https://blackhat.com/docs/us-16/materials/us-16-Chen-Subverting-Apple-Graphics-Practical-Approaches-To-Remotely-Gaining-Root-wp.pdf) supplies methods for connecting client stubs, Mach messages and server handlers, not a validated current-build atomic movement API. [iland's SDL backend](https://github.com/CoreBedtime/iland/blob/real/shims/sdl/src/sdl_backend.m) hosts its compositor in an NSWindow; it does not demonstrate presentation control of unrelated native windows. Wawona's [native application bridge](https://wawona.io/docs/user/swinging-bridge/) is described as unimplemented. Detailed attribution and the conflicting takeover claims are in [prior research](PRIOR-RESEARCH.md).

## Most useful next experiment

Before investigating or injecting into WindowServer, extend an existing isolated desktop fixture to measure the **already implemented AX-plus-update-batch path**. Use two distinguishable windows belonging to a disposable second process and a Shoji-owned, high-contrast indicator. Scope the controller to their verified process and window IDs. Drive the same repeated horizontal displacement through the current scroll tick; do not operate on the user's apps or switch Spaces. Capture the fixture area as a timestamped sequence, if Screen Recording permission is available, and log requested positions, individual AX call start/end and readback, display tick times and cleanup. Compare every captured frame against the initial inter-window pitch and indicator-to-window offset. Include repeated swipes, an interrupted reversal and a stationary control. Observe actual pixels independently of AX/SkyLight bounds; separate permission/capture failure from a negative synchronization result.

Run the current batch and an otherwise equivalent unbatched control in alternating trials; keep the same input path, sample rate and trajectories. Report per-frame maximum spacing and indicator errors, missed/stale frames and sample counts, plus display refresh and capture cadence. A captured stream has its own timing and can miss transient frames: measure its rate and avoid claiming physical display atomicity from incomplete sampling. Restore all fixture state and ensure bounded runtime and cleanup on timeout. This asks whether the **existing** batch yields adequate coordination; it does not assume that it can batch foreign AX writes.

If both runs show the same visible desynchronization, profile AX completion and application response before choosing a new mechanism. If the batched run is measurably better and meets an agreed visual tolerance, investigate integration and more applications rather than invasive hooks. If camera planning already diverges from requested frames, fix the engine before researching compositor control. If capture cannot resolve transient mismatch, retain an inconclusive result and improve measurement. A transaction-based foreign-position test is a later step only after identifying and validating a candidate position setter and its ABI; the existing Dock alpha/order transaction is not that setter.

## Preliminary foreign-window bounds control

On 2026-10-28 the existing signed `shoji --validate-swipe` ran against two disposable `size-fixture` windows in a separate process, using a temporary title-specific `manage=off` rule. It reported a 16-point baseline gap and a maximum sampled native-bounds gap error of 0 points across 30 samples; the first window moved 300 points. The diagnostic exited 0. Raw local output: `/tmp/shoji-swipe-control.3tlp9HfV/measurement.out`. The fixture process exited, its window query was empty, and the temporary rule was removed. The normal Shoji service and Dock were not restarted.

This is not the planned comparison: the existing diagnostic samples bounds after movement, rather than capturing displayed frames, and does not measure a focus indicator or provide a matched unbatched control. Its input trajectory has five 60-point movements followed by stationary samples. It cannot rule out sub-sample gaps or visual lag, establish batching's effect, or prove smoothness. The normal validation-daemon harness refuses to start alongside the running service because the lock and socket are shared; the existing paced motion lab instead uses owned windows. A separate scoped controller with a visual capture path and matched control, or isolated validation IPC, is still needed to execute the experiment described above.
